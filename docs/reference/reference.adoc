== Überblick und Features

GRETL verarbeitet Geodaten und andere strukturierte Daten: Dateien beziehen,
Daten prüfen, Datenbanken befüllen, Modelle umbauen und Ergebnisse exportieren.
Ein Job verbindet benannte Tasks zu einem gerichteten azyklischen Graphen
(DAG). GRETL wählt die benötigten Vorgänger aus und führt sie sequenziell in
einer JVM aus. Ein Job wird als Groovy-Script geschrieben; die mitgelieferte
Groovy-Laufzeit kompiliert es beim Start automatisch.

Die Standarddistribution stellt 44 Taskarten bereit. Dazu gehören HTTP-,
FTP- und S3-Transfers, SQL und Datenbanktransfers, CSV/JSON/Excel,
GeoPackage/Shapefile sowie INTERLIS- und AV-Werkzeuge. Deklarierte Parameter,
explizite Abhängigkeiten und dokumentierte Ergebnisfelder verbinden diese
Bausteine. Taskhilfe und Property-Tabellen verwenden dieselben Metadaten.
Eigene Taskbibliotheken können vor dem Start bereitgestellt werden.

Der aktuelle Stand ist [.code-fragment]#`0.1.0-SNAPSHOT`#. Die erste Zielplattform ist Linux
x86-64; zusätzliche Plattformen benötigen ihre eigenen Fach- und
Treibernachweise. Ein lokaler Lauf auf einem anderen Betriebssystem ist noch
keine allgemeine Plattformfreigabe.

GRETL besitzt keine globale Transaktion über den ganzen Job. Ein späterer
Fehler kann bereits geschriebene Dateien oder Datenbankänderungen hinterlassen.
Es gibt keinen automatischen Vollretry, Laufzeitcache oder Resume eines alten
Runs. Abbruch und Timeout sind kooperativ. Publisher, Native Image und
[.config-key]#`XtfToGpkg`# gehören nicht zum hier beschriebenen Lieferumfang.

== Systemanforderungen und Installation

=== Java und Distribution

Zum Ausführen wird Java 25 benötigt. Die Distribution enthält Groovy 6 und die
Bibliotheken ihrer Taskarten. Maven und Gradle werden beim Scriptstart nicht
benötigt. Der mitgelieferte Launcher [.code-fragment]#`bin/gretl`# ist ein Shellscript.

Die Snapshot-Artefakte stehen im
link:https://jars.interlis.guru/snapshots/ch/so/agi/gretl/gretl-dist/0.1.0-SNAPSHOT/[Snapshot-Verzeichnis].
Für die Installation das ZIP mit dem Classifier [.config-key]#`bin`# oder das TAR.GZ mit dem
Classifier [.code-fragment]#`bin-tar-gz`# herunterladen. Die
link:https://jars.interlis.guru/snapshots/ch/so/agi/gretl/gretl-dist/0.1.0-SNAPSHOT/maven-metadata.xml[Maven-Metadaten]
benennen die timestamped Snapshot-Dateien. Ein Snapshot kann durch einen
neueren Build ersetzt werden; für einen nachvollziehbaren Betrieb das
konkrete Archiv und seine Prüfsummen aufbewahren.

Nach dem Download, hier unter dem lokalen Namen [.file-name]#`gretl-runtime.zip`#:

[source,bash]
----
unzip gretl-runtime.zip
cd gretl-runtime-0.1.0-SNAPSHOT
export JAVA_HOME=/pfad/zu/jdk-25
export PATH="$JAVA_HOME/bin:$PWD/bin:$PATH"
java -version
shasum -a 256 -c SHA256SUMS
gretl --version
gretl operations
----

Unter Linux kann statt [.code-fragment]#`shasum -a 256`# auch [.config-key]#`sha256sum`# verwendet werden.
Ein TAR.GZ wird mit [.file-name]#`tar -xzf gretl-runtime.tar.gz`# entpackt. Für einen neuen
Terminalstart [.env-var]#`JAVA_HOME`# und den absoluten Pfad zu [.config-key]#`bin`# dauerhaft setzen.

[source,text]
----
bin/gretl          Startprogramm
lib/runtime/      Runtime, Groovy, Logging und CLI
lib/tasks/        Mitgelieferte Taskbibliotheken und Dependencies
lib/extensions/   Zusätzlich bereitgestellte Bibliotheken
examples/         Jobs mit lokalen Beispieldaten
inventory.json    Ausgelieferte Artefakte und Versionen
SHA256SUMS        Prüfsummen des Distributionsinhalts
----

=== Aus dem Quellcode bauen

Nur für Entwicklung oder eine selbst gebaute Distribution ist ein JDK 25
nötig. Der eingecheckte Maven-Wrapper lädt Maven selbst:

[source,bash]
----
./mvnw verify
unzip gretl-dist/target/gretl-runtime-0.1.0-SNAPSHOT-bin.zip
----

Der Build benötigt Zugriff auf die im Projekt konfigurierten Maven-Repositories.
Die normale Prüfung benötigt keine externen Datenbank-, FTP- oder S3-Dienste.
Das zusätzliche Profil [.code-fragment]#`backing-services`# prüft diese Integrationen gegen
lokale Dienstcontainer. Diese Buildaufgaben gehören nicht in ein Jobscript.

== Schnellstart

=== Eine lokale INTERLIS-Datei validieren

Die Distribution liefert einen vollständigen lokalen Modell- und Datenbestand
unter [.code-fragment]#`examples/ili-validator/`#. Der zugehörige Job lautet:

[source,groovy]
----
include::../../gretl-dist/src/main/dist/examples/ili-validator/job.groovy[]
----

Im entpackten Distributionsverzeichnis:

[source,bash]
----
gretl run examples/ili-validator/job.groovy --help
gretl check examples/ili-validator/job.groovy
gretl plan examples/ili-validator/job.groovy
gretl run examples/ili-validator/job.groovy --report ./validation-run.json
----

Bei Erfolg endet der Prozess mit Exitcode 0. Der Runbericht enthält Status,
Zeiten und Diagnoseverweise. Der Task liefert [.config-key]#`reportFile`# für den fachlichen
Prüfbericht; das ist ein anderer Bericht als [.file-name]#`validation-run.json`#.
Zwischendateien im Arbeitsbereich werden nach erfolgreichem Lauf normalerweise
entfernt. Zum Untersuchen kann der Lauf mit [.cli-option]#`--keep-work always`# gestartet
werden; dauerhaft benötigte Ergebnisse werden in einen externen Pfad kopiert.

=== Eine Datei herunterladen und entpacken

Dieser Job ist unverändert in der Beispieldistribution enthalten:

[source,groovy]
----
include::../../gretl-dist/src/main/dist/examples/download-extract/job.groovy[]
----

Die Parameter werden beim Start übergeben. Ein URL- und Zielwechsel benötigt
keinen neuen Produktbuild. [.config-key]#`dependsOn`# wählt den Download als Vorgänger aus,
und [.code-fragment]#`result('download').file`# reicht seine abgeschlossene Datei weiter.

Zum lokalen Ausprobieren kann ein einfacher HTTP-Server das mitgelieferte
Archiv anbieten. Python wird nur für diesen Testserver gebraucht. Im ersten
Terminal im Distributionsverzeichnis:

[source,bash]
----
python3 -m http.server 8765 --bind 127.0.0.1 --directory examples/download-extract
----

Im zweiten Terminal, ebenfalls im Distributionsverzeichnis:

[source,bash]
----
gretl run examples/download-extract/job.groovy \
  --param quelle=http://127.0.0.1:8765/data.zip \
  --param ziel=./entpackt \
  --report ./download-run.json
----

Das Zielverzeichnis soll für diese Probe noch nicht existieren. Vorhandene
Dateien werden vom Extract-Task nicht still ersetzt. Den Testserver danach
mit Ctrl-C beenden. Für einen Fachjob wird die lokale Adresse durch die
gewünschte Datenquelle ersetzt.

== Job-DSL

Die folgenden Auszüge erklären einzelne Sprachmittel. Ein Block mit einer
Parameterdeklaration allein ist noch kein vollständiger Job. Vollständige
Einstiegsjobs stehen im Schnellstart; vollständige Taskbeispiele in der Taskreferenz.

=== Tasks, Ziele und Abhängigkeiten

Ein Task wird über seinen Namen und seine Taskart registriert. Die
Einstellungen stehen als [.code-fragment]#`name = wert`# im Block. Die Konfiguration wird erst
gelesen, wenn der Task nach seinen Vorgängern an der Reihe ist.

[source,groovy]
----
task('update', SqlExecutor) {
    database = 'edit'
    scripts = [file('sql/update.sql')]
}

defaults 'update'
----

[.config-key]#`dependsOn`# nennt einen oder mehrere Vorgänger. Die Runtime ermittelt daraus
die Auswahlhülle; sie errät keine Abhängigkeit aus einem späteren
Ergebniszugriff.

[source,groovy]
----
task('download', HttpDownload) {
    url = 'https://example.invalid/data.zip'
    output = workPath('data.zip')
}

task('extract', Extract, dependsOn: 'download') {
    archive = result('download').file
    compression = 'ZIP'
    outputDirectory = workPath('entpackt')
}

defaults 'extract'
----

Quellreihenfolge im Script ist nur Lesbarkeit. Sie ersetzt keine
[.config-key]#`dependsOn`#-Kante. [.config-key]#`after`# ist eine reine Reihenfolge zwischen bereits
ausgewählten Tasks und erzeugt keinen Ergebniszugriff.

=== Parameter

Öffentliche Jobparameter werden einmal im Script deklariert. [.config-key]#`description`# ist
Pflicht; [.config-key]#`type`# ist [.config-key]#`text`#, [.config-key]#`boolean`#, [.config-key]#`integer`# oder [.dsl-method]#`path`#.

[source,groovy]
----
parameter('quelle', required: true,
          description: 'Adresse der ZIP-Datei')
parameter('entpacken', type: 'boolean', defaultValue: true,
          description: 'Das Archiv nach dem Download entpacken')
----

Werte werden mit [.cli-option]#`--param name=wert`# oder über eine Parameterdatei übergeben.
Deklarierte Pfadparameter werden relativ zum ursprünglichen Startverzeichnis
aufgelöst. [.config-key]#`run`# prüft alle verpflichtenden Parameter vor der ersten
Taskarbeit. [.config-key]#`check`# und [.config-key]#`plan`# dürfen fehlende Pflichtwerte noch als offen
anzeigen.

=== Pfade

Die Job-DSL kennt drei Pfadbereiche:

- [.dsl-method]#`file('...')`# bezeichnet eine Datei oder ein Verzeichnis, das zum Job gehört.
- [.dsl-method]#`workPath('...')`# bezeichnet eine temporäre Arbeitsdatei des aktuellen
  Tasks. Der Pfad bleibt für nachfolgende Tasks bis zum Runende lesbar.
- [.dsl-method]#`path('...')`# löst einen erst im Job entstandenen externen Pfad relativ zum
  Startverzeichnis auf.

Ein deklarierter Parameter vom Typ [.dsl-method]#`path`# liefert direkt einen aufgelösten
[.java-type]#`Path`#. [.dsl-method]#`file`#, [.dsl-method]#`workPath`# und [.dsl-method]#`path`# öffnen die Datei nicht; sie liefern nur
den Pfad. Ob eine Operation eine vorhandene Ausgabe überschreiben darf, regelt
die jeweilige Taskart.

=== Ergebnisse

Ein Task kann dokumentierte Ergebnisse bereitstellen. Der Zugriff erfolgt über
[.code-fragment]#`result('name').feld`# und ist nur entlang einer direkten oder transitiven
[.config-key]#`dependsOn`#-Kette erlaubt.

[source,groovy]
----
task('download', HttpDownload) {
    url = 'https://example.invalid/data.zip'
    output = workPath('data.zip')
}

task('extract', Extract, dependsOn: 'download') {
    archive = result('download').file
    compression = 'ZIP'
    outputDirectory = workPath('entpackt')
}
----

[.dsl-method]#`result`# startet keinen Task und ergänzt keine Kante. Unbekannte Felder,
fehlende Vorgänger und ein Zugriff auf einen übersprungenen oder
fehlgeschlagenen Task sind Fehler. Die Hilfe von [.command]#`gretl operations <Symbol>`#
nennt die verfügbaren Ergebnisfelder.

=== Actions

Eine Action ist gewöhnlicher ausführbarer Groovy-Code. Sie kann Tasks synchron
mit [.code-fragment]#`ctx.run(...)`# aufrufen und deren Javaresultate weiterverarbeiten. Eine
Action kann mit [.literal]#`null`# erfolgreich enden; ein nicht-void Taskhandler mit
deklarierter Ergebnisstruktur darf dagegen nicht unbemerkt [.literal]#`null`# liefern.

[source,groovy]
----
action('pruefen') {
    def result = ctx.run(IliValidator) {
        dataFile = file('data/valid.xtf')
        modelDirectory = file('models')
    }
    println 'Warnungen: ' + result.warnings()
}
----

Actions und Tasks verwenden denselben Plan, dieselben Ergebnisse und dieselben
Fehlerregeln. Eine Action ist keine zweite Ablauf-DSL.

=== Bedingungen und kontrolliertes Jobende

[.config-key]#`when`# wird unmittelbar vor der Taskkonfiguration ausgewertet. Bei [.literal]#`false`#
bleibt die Konfiguration unausgeführt und der Task wird [.literal]#`SKIPPED`#. Ein
Nachfolger kann weiterlaufen, muss aber das fehlende Ergebnis bewusst behandeln.
[.config-key]#`after`# ordnet nur bereits ausgewählte Tasks und erlaubt keinen Resultatzugriff.

Dieses vollständige lokale Beispiel beendet den Job bewusst ohne Daten:

[source,groovy]
----
include::../../gretl-dist/src/main/dist/examples/action-nodata/nodata.groovy[]
----

Ein solches Ende ergibt nach erfolgreichem Cleanup [.literal]#`NO_DATA`# und Exitcode 0.
Ein Downloadfehler ist kein Nachweis fehlender Daten und wird nicht auf diese
Weise in einen Erfolg umgedeutet. Ein [.config-key]#`return`# im Konfigurationsblock ist kein Skip.

=== Cleanup und Fehlerbehandlung

[.code-fragment]#`cleanup('name') { ... }`# registriert Arbeit für das Runende. Die Aktionen laufen
in umgekehrter Registrierungsreihenfolge nach Erfolg, Fehler, NO_DATA und
kooperativem Abbruch. Sie laufen nicht bei [.config-key]#`check`#, [.config-key]#`plan`# oder einem Fehler
vor dem Run. Im Cleanup sind keine neuen Tasks und keine [.code-fragment]#`ctx.run`#-Aufrufe erlaubt.
Fachliche Erfolgsschritte wie das Löschen erfolgreich verarbeiteter Quelldaten
gehören in den normalen Ablauf, da Cleanup auch nach einem Fehler läuft.

Eine Action darf einen Fachfehler mit normalem [.code-fragment]#`try/catch`# behandeln. Ein
unbehandelter Fehler oder ein erforderlicher Freigabefehler lässt den Task
fehlschlagen. Ein Cleanupfehler kann einen sonst erfolgreichen Run noch
scheitern lassen. Alle bereits erzeugten Fachwirkungen bleiben real.

== Kommandoreferenz

=== Hilfe, Version und Taskkatalog

[cols="3,5",options="header"]
|===
| Aufruf | Bedeutung
| [.command]#`gretl --help`# | Globale Hilfe; lädt weder Job noch Taskprovider.
| [.command]#`gretl --version`# | Runtimeversion, Paketidentität und erforderliche Java-Linie.
| [.command]#`gretl operations`# | Tatsächlich verfügbare Taskarten mit Beschreibung und Herkunft.
| [.command]#`gretl operations SqlExecutor`# | Felder, Defaults, erlaubte Werte, Ergebnisse und Beispiel dieser Taskart.
| [.command]#`gretl run job.groovy --help`# | Deklarierte Parameter und Ziele des Jobs; keine Taskarbeit.
|===

Die Jobhilfe lädt das vertrauenswürdige Groovy-Script. Code ausserhalb der
Taskblöcke kann dabei ausgeführt werden. Sie löst keine Secretwerte auf und
verlangt keine Pflichtparameter. Syntax- und Registrierungsfehler bleiben Fehler.

[.code-fragment]#`operations --format adoc --lang de --output <verzeichnis>`# erzeugt die
Property-Tabellen des geladenen Katalogs. Mit einem einzelnen Symbol kann die
Tabelle auch auf stdout ausgegeben werden. Beschreibungen und vollständige
Beispiele der Referenz werden redaktionell gepflegt.

=== Definition prüfen, Plan anzeigen, Job ausführen

[source,bash]
----
gretl check job.groovy
gretl plan job.groovy --target export
gretl plan job.groovy --graph mermaid --output ./plan.mmd
gretl plan job.groovy --graph plantuml --output ./plan.puml
gretl run job.groovy --target export --report ./run.json
----

[.config-key]#`check`# prüft die verfügbare Definition. [.config-key]#`plan`# bildet zusätzlich den Plan der
gewählten Ziele und ihrer Vorgänger. Beide führen keine Taskkonfiguration,
Taskarbeit oder Cleanup aus. Fehlende Pflichtparameter dürfen noch offen
bleiben; ausdrücklich angegebene Werte müssen bereits zum Parametertyp passen.
Toplevelcode des Scripts wird auch hier geladen: Diese Befehle sind keine
Sandbox und prüfen keine erst später entstehenden Fachwerte.

[.config-key]#`run`# prüft alle jobweit erforderlichen Parameter vor dem ersten Task, auch
wenn nur ein Teilziel gewählt wurde. Ohne [.cli-option]#`--target`# gelten die mit [.dsl-method]#`defaults`#
registrierten Ziele. Fehlt beides, endet der Aufruf als Konfigurationsfehler.

|===
| Option | Wirkung
| [.cli-option]#`--target <name>`# | Wiederholbar; explizite Ziele statt Scriptdefaults.
| [.cli-option]#`--config <datei>`# | Eine explizite UTF-8-JSON-Runtimekonfiguration.
| [.cli-option]#`--params-file <datei>`# | JSON-Objekt mit Jobparameterwerten als Strings.
| [.cli-option]#`--param <name=wert>`# | Wiederholbare Parameterübergabe; trennt am ersten Gleichheitszeichen.
| [.cli-option]#`--work-dir <verzeichnis>`# | Wurzel für die privaten Arbeitsbereiche eines Runs.

| [.cli-option]#`--keep-work <modus>`# | [.config-key]#`never`#, [.code-fragment]#`on-failure`# oder [.config-key]#`always`#; Vorgabe [.code-fragment]#`on-failure`#.

| [.cli-option]#`--log-level <level>`# | [.literal]#`TRACE`#, [.literal]#`DEBUG`#, [.literal]#`INFO`#, [.literal]#`WARN`# oder [.literal]#`ERROR`#.

| [.cli-option]#`--graph mermaid\|plantuml`# | Graphdarstellung bei [.config-key]#`plan`#; mit [.cli-option]#`--output`# in eine Datei schreiben.
| [.cli-option]#`--output <pfad>`# | Graphdatei bei [.config-key]#`plan`#, Tabellenverzeichnis bei [.config-key]#`operations`# oder JAR bei [.config-key]#`package`#.
|===

Optionen sind befehlsspezifisch. Beispielsweise akzeptiert [.config-key]#`check`# keinen
Runbericht und startet keine Deadline. Unbekannte oder unpassende Optionen,
fehlende Optionswerte und doppelte Parameternamen in derselben Quelle sind
Fehler. Dateipfade in CLI-Optionen beziehen sich auf das Startverzeichnis.
Werte mit Leerzeichen als ein Shellargument quotieren:

[source,bash]
----
gretl run job.groovy --param 'ziel=/data/Meine Ergebnisse'
----

=== Paketieren

[source,bash]
----
gretl package job-package.json --output job.jar
java -jar job.jar --help
java -jar job.jar --report ./run.json
----

[.config-key]#`package`# erhält einen Paketdeskriptor und benötigt [.cli-option]#`--output`#. Die Paketierung
kompiliert den Job, führt ihn aber nicht aus. Der Abschnitt
<<job-jars,Job-JARs>> beschreibt Ressourcen und Abhängigkeiten.

== Konfiguration und Betrieb

=== Runtimekonfiguration

Ein Job darf ohne [.cli-option]#`--config`# starten. Dann gibt es keine vorbereiteten
Secret- oder Datenbankaliase, kein Jobzeitlimit und Textlogging auf stderr mit
INFO. Arbeitsbereiche liegen unter [.code-fragment]#`gretl-work`# im Java-Temporärverzeichnis;
Runberichte unter [.code-fragment]#`gretl-reports`# im Startverzeichnis. [.config-key]#`keepWork`# ist
[.code-fragment]#`on-failure`#.

Eine vollständige Beispielkonfiguration mit einer Datenbankverbindung:

[source,json]
----
{
  "schemaVersion": 1,
  "language": "de",
  "runtime": {
    "workRoot": "./work",
    "reportRoot": "./reports",
    "keepWork": "on-failure",
    "timeout": "PT1H",
    "jobName": "datenbezug"
  },
  "logging": {
    "format": "text",
    "level": "INFO",
    "eventFile": true
  },
  "params": {"umgebung": "test"},
  "secrets": {
    "dbPassword": {"environment": "GRETL_DB_PASSWORD"},
    "sourceAuth": {"file": "./secrets/source-auth.txt"}
  },
  "taskConfig": {
    "edit": {
      "jdbcUrl": "jdbc:postgresql://localhost/gretl_test",
      "user": "gretl_test",
      "passwordSecret": "dbPassword"
    }
  }
}
----

Unbekannte Corefelder, doppelte JSON-Schlüssel und falsche Typen werden
abgelehnt. Für den Inhalt eines [.config-key]#`taskConfig`#-Alias ist die verwendende Taskart
verantwortlich. [.code-fragment]#`database = 'edit'`# bezeichnet im Beispiel diesen Alias;
JDBC-URL und Passwort stehen nicht im Job. Weitere Datenbanktasks verwenden
entsprechend ihre dokumentierten Aliasfelder. Verbindung und fachlich
benötigte Tabellen müssen vorbereitet sein.

=== Parameter und Prioritäten

Öffentliche Jobparameter werden im Script einmal mit Beschreibung deklariert.
Die Typen sind [.config-key]#`text`#, [.config-key]#`boolean`#, [.config-key]#`integer`# und [.dsl-method]#`path`#. [.config-key]#`integer`# liefert einen
64-Bit-Long; [.config-key]#`boolean`# akzeptiert nur [.literal]#`true`# und [.literal]#`false`#. [.dsl-method]#`path`# liefert einen
normalisierten Path, ohne die Existenz einer Datei vorwegzunehmen.

Vorrang von niedrig nach hoch:

. [.config-key]#`defaultValue`# in der Jobdeklaration.
. [.config-key]#`params`# in der Runtimekonfiguration.
. Werte aus [.cli-option]#`--params-file`#.
. Werte aus [.cli-option]#`--param`#.

Parameterdatei und Runtime-[.config-key]#`params`# enthalten Stringwerte, beispielsweise:

[source,json]
----
{"jahr": "2026", "vollstaendig": "true", "ziel": "./ausgabe"}
----

[.code-fragment]#`required: true`# und [.config-key]#`defaultValue`# dürfen nicht kombiniert werden. Ein
optionaler Parameter ohne Wert liefert [.literal]#`null`#. Ein leerer optionaler Text ist
ein Wert; ein erforderlicher Text darf nicht leer sein. Unbekannte Namen in
[.cli-option]#`--param`# oder der Parameterdatei sind Fehler. Zusätzliche Namen in der
allgemeinen Runtimekonfiguration werden für diesen Job ignoriert.
JSON-Werte werden weder als Groovy-Ausdruck noch mit Variablenersetzung ausgeführt.

=== Pfadbasen und Arbeitsbereiche

[cols="3,5",options="header"]
|===
| Pfad | Basis
| Jobdatei und CLI-Dateioptionen | Ursprüngliches Startverzeichnis.
| [.config-key]#`runtime`#-Pfade und Secretdateien | Verzeichnis der Runtimekonfiguration.
| [.dsl-method]#`file('...')`# | Jobverzeichnis; im Job-JAR die materialisierten Ressourcen.
| [.dsl-method]#`parameter('ziel')`# mit Typ [.dsl-method]#`path`# | Ursprüngliches Startverzeichnis, auch bei Übergabe aus einer Parameterdatei.
| [.dsl-method]#`path('...')`# | Ursprüngliches Startverzeichnis.
| [.dsl-method]#`workPath('...')`# | Privater Arbeitsbereich des aktuellen Tasks oder synchronen Aufrufs.
|===

Jeder Run erhält einen eigenen Arbeitsbereich. Zwischenergebnisse bleiben für
Nachfolger bis zum Runende zugänglich. [.dsl-method]#`workPath`# verlangt relative Pfade,
verhindert das Verlassen des Arbeitsbereichs und erstellt erforderliche
Elternverzeichnisse. Es erstellt keine fertige Ausgabedatei.
Ergebnisse, die den Run überleben sollen, gehören in ein ausdrücklich gewähltes
externes Ziel. Mit [.cli-option]#`--keep-work always`# lassen sich Arbeitsdateien untersuchen.

=== Secrets und Sprache

Ein Secretalias verweist entweder auf eine Environmentvariable oder auf eine
Datei. Die Quelle wird erst beim Zugriff mit [.dsl-method]#`secret('alias')`# gelesen.
Secretdateien sind UTF-8, höchstens 64 KiB gross; ein abschliessendes LF oder
CRLF wird entfernt. Environmentwerte werden unverändert gelesen.
[.java-type]#`SecretValue`# wird von unterstützten Taskfeldern direkt angenommen. Seine
Stringdarstellung ist maskiert; ein Passwort deshalb nicht durch gewöhnliche
Stringkonkatenation in einen Header einbauen.

Öffentliche Parameter und deren Defaults sind kein Secretkanal. Verwaltete
Logs und Berichte maskieren bekannte Secretwerte. Frei programmierte Ausgaben
oder absichtlich kodierte Geheimnisse können diesen Schutz umgehen.

Die Sprache wird in folgender Reihenfolge gewählt:
[.cli-option]#`--lang`# vor [.env-var]#`GRETL_LANGUAGE`# vor [.config-key]#`language`# in der Runtimekonfiguration vor
der Betriebssystem-Locale. Ohne unterstützte Locale ist Englisch der Fallback.
Technische Feldnamen, IDs und Fehlercodes bleiben sprachneutral.

=== Logging, Berichte und Exitcodes

Konsole, Ereignisdatei und Abschlussbericht erfüllen unterschiedliche Aufgaben:

* Text- oder JSON-Konsolenlogs gehen auf stderr; Hilfe und Planausgabe auf stdout.
* Die begrenzte Ereignisdatei [.code-fragment]#`<runId>.events.jsonl`# liegt im Reportverzeichnis.
  [.code-fragment]#`logging.eventFile=false`# deaktiviert sie.
* Der erforderliche Abschlussbericht heisst [.file-name]#`<runId>.json`# oder verwendet den
  Pfad aus [.cli-option]#`--report`#. Er enthält Taskstatus, Zeiten und explizite Diagnosen.

Der Bericht serialisiert keine beliebigen Taskresultate und ist kein
Wiederaufnahmespeicher. Globale Hilfe, Jobhilfe, [.config-key]#`check`# und [.config-key]#`plan`# erzeugen
keinen Runbericht. Für einen fehlgeschlagenen Run sind Taskname, betroffenes
Feld, Quelle und Ursachen wichtiger als ein einzelner Log-Level: Eine Action
kann einen Fachfehler bewusst behandeln und trotzdem erfolgreich enden.

[cols="1,6",options="header"]
|===
| Exitcode | Bedeutung
| 0 | Erfolgreicher Run oder bewusstes [.literal]#`NO_DATA`# nach erfolgreichem Cleanup.
| 2 | CLI-, Konfigurations-, Lade- oder Planfehler vor Beginn des Runs.
| 10 | Unbehandelter Task-, Request-, Fach- oder Cleanupfehler nach Runbeginn.
| 20 | Kontrollierter Abbruch oder Timeout.
| 40 | Nachgewiesener interner Runnerfehler.
|===

Ein später falsches Taskfeld ist ein Laufzeitfehler; [.config-key]#`check`# führt seine
Konfigurationsclosure nicht vorab aus. Nach einem unbehandelten Taskfehler
beginnt keine weitere normale Taskarbeit. Cleanup wird noch versucht.
Timeout beendet eine nicht kooperierende In-Process-Bibliothek nicht hart.
Nach einem erzwungenen Prozessende können Cleanup und Abschlussbericht fehlen.
Vor einem erneuten Lauf sind die Diagnosen der Taskart und bereits erfolgte
Fachänderungen zu beachten.

[[task-curl]]
=== Curl

[.task-type]#`Curl`# führt genau eine HTTP-Anfrage aus und prüft die Antwort. Der Task ist
für API-Aufrufe, Uploads, Token-Abrufe und Response-Assertions gedacht. Im
Gegensatz zu [.task-type]#`HttpDownload`# ist das Ziel optional und der Status wird exakt
geprüft.

[cols="2,3,3",options="header"]
|===
|Aspekt |[.task-type]#`HttpDownload`# |[.task-type]#`Curl`#
|Rolle |Datei herunterladen und sicher veröffentlichen |HTTP-Anfrage ausführen und Antwort prüfen
|Ausgabe |[.config-key]#`output`# Pflicht |[.config-key]#`outputFile`# optional
|Request-Body |[.config-key]#`bodyText`# nur POST |[.config-key]#`data`#, [.config-key]#`dataBinary`# oder [.config-key]#`formData`# (multipart)
|Authentifizierung |Header mit Text/[.java-type]#`SecretValue`# |Basic Auth plus Header/[.java-type]#`SecretValue`#
|Response-Prüfung |Status 2xx, [.config-key]#`maxBytes`#, SHA-256 |exakter [.config-key]#`expectedStatusCode`#, [.config-key]#`expectedBody`#
|Ergebnisse |[.dsl-method]#`file`#, [.config-key]#`finalUri`#, [.config-key]#`status`#, [.config-key]#`bytes`#, [.config-key]#`sha256`# |[.config-key]#`status`#, [.config-key]#`bytes`#, [.config-key]#`outputFile`#
|===

Ein Token-Abruf mit Text-Body und optionaler Zieldatei:

[source,groovy]
----
task('token', Curl) {
    serverUrl = 'https://example.invalid/oauth2/token'
    method = 'POST'
    expectedStatusCode = 200
    data = 'grant_type=client_credentials'
    user = 'api-user'
    password = secret('apiPassword')
    outputFile = workPath('token.json')
}

defaults 'token'
----

Ein Multipart-Upload mit Text- und Dateifeld:

[source,groovy]
----
task('upload', Curl) {
    serverUrl = 'https://example.invalid/import'
    method = 'POST'
    expectedStatusCode = 200
    expectedBody = '"success":true'
    formData = [
        topic: 'npl',
        lv95_file: file('data.xtf.zip'),
        publish: 'true'
    ]
}

defaults 'upload'
----

Genau eines von [.config-key]#`data`#, [.config-key]#`dataBinary`# und [.config-key]#`formData`# ist zulässig. Ohne
[.config-key]#`method`# wird GET für Anfragen ohne Body und POST für Anfragen mit Body
verwendet; GET zusammen mit einem Body ist ein Fehler. Redirects werden nicht
verfolgt, und ein fehlgeschlagener Request wird nicht automatisch wiederholt.

Der Response-Body wird höchstens bis [.config-key]#`maxBytes`# gelesen (Vorgabe 16 MiB). Ein
Status ausserhalb des erwarteten Codes, ein nicht gefundener [.config-key]#`expectedBody`#
oder eine überschrittene Grenze führen zu einem Taskfehler. [.config-key]#`outputFile`# wird
erst nach erfolgreicher Prüfung atomar veröffentlicht; vorhandene Dateien
werden ohne [.code-fragment]#`overwrite = true`# nicht ersetzt. Ohne [.config-key]#`outputFile`# wird der Body
nach der Prüfung verworfen und ist kein Resultatfeld.

[.config-key]#`password`# ist ein [.java-type]#`SecretValue`# aus [.dsl-method]#`secret('alias')`# und erscheint nicht im
Klartext in Logs oder Fehlern. Ein expliziter [.config-key]#`Authorization`#-Header und Basic
Auth schliessen sich aus.

Ergebnisse sind [.config-key]#`status`#, [.config-key]#`bytes`# und [.config-key]#`outputFile`# (nullable). Die
Property-Tabelle fasst die Felder zusammen:

[[task-extract]]
=== Extract

[.task-type]#`Extract`# entpackt ein ZIP- oder GZIP-Archiv. Der Modus wird ausdrücklich über
[.config-key]#`compression`# gewählt; die Endung allein genügt nicht. ZIP schreibt in ein
Ausgabeverzeichnis, GZIP in eine einzelne Zieldatei.

[source,groovy]
----
task('extract', Extract) {
    archive = file('data.zip')
    compression = 'ZIP'
    outputDirectory = workPath('entpackt')
}

defaults 'extract'
----

Der Task schützt vor Pfad-Traversal, absoluten Einträgen, Symlinks und
kollidierenden Dateinamen. Vorhandene Zieldateien werden nicht still
überschrieben. Die Standardgrenzen liegen bei 4 GiB entpackten Daten und
10'000 ZIP-Einträgen; beide Werte sind konfigurierbar.

Ergebnisse sind [.dsl-method]#`file`#, [.config-key]#`files`#, [.config-key]#`directory`# und [.config-key]#`bytes`#. Bei GZIP ist [.dsl-method]#`file`#
die einzelne Ausgabedatei und [.config-key]#`directory`# ist [.literal]#`null`#; bei ZIP ist [.config-key]#`directory`#
das Ausgabeverzeichnis, [.dsl-method]#`file`# ist [.literal]#`null`# und [.config-key]#`files`# enthält die
abgeschlossenen regulären Dateien in stabiler Reihenfolge.

.Ergebnisfelder
[cols="2,5,1",options="header",role="gretl-task-results"]

[[task-sqlexecutor]]
=== SqlExecutor

[.task-type]#`SqlExecutor`# führt SQL-Scripts oder vorbereitete Statements gegen eine
vorbereitete PostgreSQL-Verbindung aus. Die Verbindung wird im Job nicht mit
URL und Passwort konfiguriert, sondern über einen Alias aus der
Runtimekonfiguration ([.config-key]#`taskConfig`#).

[source,groovy]
----
task('update', SqlExecutor) {
    database = 'edit'
    scripts = [file('sql/update.sql')]
}

defaults 'update'
----

Genau eine der Listen [.config-key]#`scripts`# oder [.config-key]#`statements`# muss nicht leer sein. Die
Reihenfolge der Einträge ist die Ausführungsreihenfolge. Ein Script wird als
vollständige UTF-8-Datei an den Treiber übergeben; die Runtime zerlegt es nicht
mit einem Regex in Einzelstatements. [.config-key]#`statements`# verwendet Maps mit genau den
Feldern [.config-key]#`sql`# und [.config-key]#`parameters`#.

[source,groovy]
----
task('kennzeichnen', SqlExecutor) {
    database = 'edit'
    statements = [
        [sql: 'UPDATE demo.gemeinde SET geprueft = ? WHERE bfs_nr = ?',
         parameters: [true, 2545]]
    ]
}

defaults 'kennzeichnen'
----

Alle Einträge eines Aufrufs laufen in einer Transaktion mit deaktiviertem
Auto-commit. Ein normaler Abschluss führt zu einem Commit; bei einem Fehler
wird ein Rollback versucht. Ein zusätzlicher Rollbackfehler bleibt sichtbar.
Der Task führt keinen automatischen Vollretry aus und garantiert nicht, dass
bereits erfolgte externe Wirkungen verschwinden.

Ergebnisse sind [.config-key]#`executionCount`# und [.config-key]#`executions`#. [.config-key]#`executionCount`# zählt die
übergebenen Script-/Statementeinträge, nicht einzelne SQL-Befehle.
[.config-key]#`executions`# enthält pro Eintrag die Updatezahlen und die Anzahl der
verarbeiteten ResultSets in Eingabereihenfolge.

.Ergebnisfelder
[cols="2,5,1",options="header",role="gretl-task-results"]

| Anzahl Script-/Statementeintraege

Vorhandene Ausgaben werden standardmässig ersetzt; [.code-fragment]#`overwrite = false`# lässt
den Task bei einer vorhandenen Zieldatei scheitern.

Externe Entities, DOCTYPE-Deklarationen und Netzwerkzugriffe sind deaktiviert.
Lokale Stylesheet-Includes relativ zur Stylesheetdatei bleiben zulässig.
Ergebnisse sind [.config-key]#`files`# (geschriebene Dateien in Eingabereihenfolge) und
[.config-key]#`count`#.

== Erweiterungen und Job-JARs

=== Eigene Taskbibliotheken bereitstellen

Eine Erweiterung implementiert die gradlefreie Java-SPI mit [.java-type]#`OperationProvider`#,
[.java-type]#`OperationType`#, Builder, Handler und ausdrücklich beschriebenen Ein- und
Ausgängen. Sie registriert ihren Provider über
[.code-fragment]#`META-INF/services/ch.so.agi.gretl.runtime.api.OperationProvider`#.
Das Repository enthält unter [.code-fragment]#`examples/file-size-extension`# ein separat
gebautes Beispiel.

Vor dem nächsten Start legt der Betrieb das Erweiterungs-JAR und seine
kompatiblen Abhängigkeiten in [.code-fragment]#`lib/extensions`#. Danach zeigt
[.command]#`gretl operations`# das neue Symbol samt Herkunft; seine Felder und Ergebnisse
werden auf dieselbe Weise wie bei Standardtasks dokumentiert. Doppelte IDs
oder Symbole sind Fehler. Die Verzeichnisse bilden einen gemeinsamen
Klassenpfad und bieten keine Classloader-Isolation.

Während eines Jobs werden keine JARs nachgeladen; [.code-fragment]#`@Grab`# ist deaktiviert.
Jobautoren konfigurieren die eingerichteten Bausteine und müssen selbst keine
Bibliotheksabhängigkeiten verwalten. Änderungen am Script benötigen keinen
Neubau der Runtime.

[[job-jars]]
=== Job-JARs

Ein Job-JAR enthält einen vorkompilierten Job, seine Runtime, die ausgewählten
Taskbibliotheken und deklarierte Ressourcen. Java 25 bleibt erforderlich;
eine separate GRETL-Installation, Maven oder Gradle ist beim Start nicht nötig.

Die Beispieldistribution liefert diesen Deskriptor für den lokalen Validator:

[source,json]
----
include::../../gretl-dist/src/main/dist/examples/ili-validator/job-package.json[]
----

[.config-key]#`entryScript`#, [.config-key]#`sources`# und [.config-key]#`resources`# sind relativ zum Deskriptor.
[.config-key]#`dependencies`# nennt die ausdrücklich benötigten Maven-Artefakte. Beim
Paketbuild werden sie aus dem lokalen Repository beziehungsweise den
unterstützten Repositories aufgelöst. Ein fehlendes Artefakt ist ein Fehler;
die Paketierung führt den Job nicht aus, um Abhängigkeiten zu erraten.

[source,bash]
----
gretl package examples/ili-validator/job-package.json --output ./ili-job.jar
java -jar ili-job.jar --help
java -jar ili-job.jar --report ./ili-run.json
----

Bei einem noch nicht veröffentlichten Snapshot müssen die benötigten
Artefakte zuerst bereitgestellt oder mit [.command]#`./mvnw install`# im lokalen
Maven-Repository installiert werden. Im Job-JAR gelten dieselben
Parameterregeln und Pfadbasen wie beim Scriptstart. [.dsl-method]#`file('models')`# liest aus
den materialisierten Paketressourcen. Das JAR enthält einen festen Jobstand;
eine Scriptänderung verlangt einen neuen Paketbuild.

== Referenz pflegen

Die Dateien unter [.code-fragment]#`generated/`# enthalten ausschliesslich Property-Tabellen.
Sie werden aus dem tatsächlich ausgelieferten Taskkatalog erzeugt:

[source,bash]
----
./scripts/generate-task-docs.sh
./mvnw verify
----

Beschreibungstexte, Beispiele, Ergebnisfelder und Verweise in dieser Hauptdatei
werden redaktionell gepflegt. Neue Taskarten benötigen ein vollständiges
Kapitel und ein Include ihrer generierten Tabelle. Die Prüfung vergleicht die
generierten Dateien mit der Distribution und prüft sämtliche Tabellen-Includes.
Die Autorenanleitung in [.code-fragment]#`docs/reference/README.md`# beschreibt den lokalen
Thoth-Build und die Vorschau; [.code-fragment]#`STYLE_GUIDE.md`# legt Schreibweise und Gestaltung fest.
